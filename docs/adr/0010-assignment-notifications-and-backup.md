# ADR-0010: Оповещения о публикации и резервное копирование volume

- Дата: 2026-10-31
- Статус: принято пользователем в составе плана assignment-rules
- План: [2026-10-30-assignment-rules.md](../plans/2026-10-30-assignment-rules.md)
- Контракт: [assignment-rules.md](../contracts/assignment-rules.md)

## Контекст

Участникам нужно узнавать о новых заданиях лично с учётом тихих часов.
Список «Все» должен показывать оставшуюся актуальную работу. Обновление
существующей outbox требует расширить CHECK, сохранив все данные. Сервер
получает только Docker-образы, Go/Make и shell в runtime отсутствуют.

## Решение

Использовать новый вид assignment_created в общей durable outbox. Получатели
определяются при публикации; актуальность и настройки проверяются перед HTTP.
Общие lease/retry/rate limiter сохраняются. Перепланирование reminder отделено
от отмены всех личных уведомлений. События старых заданий не создаются.

Миграция 0004 выполняет create-copy-drop-rename с переносом всех 18 прежних
полей и nullable assignment_id. Старые миграции неизменны. Down отказывает
при наличии нового вида, не отбрасывая события ради совместимости.

В списке «Все» service задаёт personal pending и deadline>now, SQL фильтрует
до пагинации. Данные не удаляются. Кнопки показывают темы без смены callback.

Один образ содержит /app/bot и /app/backup. Одноразовый Compose-сервис backup
под профилем maintenance архивирует весь data volume только при остановленном
боте. Data подключён read-only, архивы пишутся на хост, сеть и токен не нужны.
Root служебного процесса обеспечивает чтение файлов UID 65532 и восстановление
владельца. Уменьшены capabilities, rootfs read-only, Docker socket не передаётся.
Restore разрешён только в пустой новый volume. Управление остановкой, обновлением
и переключением volume остаётся явными командами оператора из инструкции.

## Последствия

Новый тип события использует существующий worker; отдельный cron не требуется.
Как и у reminder, crash после Telegram accept до ack может привести к дублю.
Механизмы SQL-транзакций не тестируются отдельно; проверяется сохранность всех
полей миграции и прикладное поведение очереди. Бэкап требует короткой остановки.
Проверенные архивы нужно хранить также вне сервера. Расписание и retention
не входят в изменение. Старый образ нельзя запускать на новой БД как способ
отката: используется копия до обновления и соответствующий прежний образ.
