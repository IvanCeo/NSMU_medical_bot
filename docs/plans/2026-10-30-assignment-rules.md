# Оповещения о новых заданиях и правила списка «Все»

Статус: утверждено пользователем 2026-10-31, включая миграцию и резервное копирование.
Реализовано; Lead review выполнен. [Отчёт проверок](2026-10-31-assignment-rules-verification.md).
Ветка: `chore`.
Контракты: [assignment-rules.md](../contracts/assignment-rules.md).

## Подтверждено пользователем

- Оповещения о новых заданиях отправляются лично участникам группы,
  с учётом настроек и тихих часов. В группе остаётся только дайджест.
- Выполненное или просроченное задание скрывается из обычного списка «Все».
- Кнопки открытия называются темами заданий.
- Предусмотреть одноразовый вспомогательный контейнер для резервной копии БД.
- Механизм SQL-транзакций отдельно не тестировать; проверять нашу миграцию
  и сохранность данных.

## Поведение

После подтверждения публикации задание, будущие напоминания, оповещения
и аудит сохраняются одной транзакцией. Уведомление получают участники группы
на момент публикации, которым доступен личный чат и включены личные уведомления.
Автор тоже получает оповещение, если сам состоит в этой группе.

Вне тихих часов отправка начинается через существующий worker сразу после
публикации; в тихие часы — после их завершения. Если отправка не успевает
до дедлайна, она пропускается. Сообщение: «Новое задание», предмет, тема и срок,
кнопка с темой открывает актуальную карточку. Файлы автоматически не рассылаются.

Создание формирует событие один раз. Редактирование не создаёт новую рассылку;
ещё не отправленное оповещение показывает актуальную тему и срок. Изменение
тихих часов перепроверяется перед отправкой. Выполнение задания, отмена,
выход/исключение из группы, выключение уведомлений и блокировка бота прекращают
ожидающую доставку. Undo и повторное включение не рассылают старые оповещения.
Вступившие позже и задания, существовавшие до обновления, не получают рассылку
задним числом. Для них сохраняются обычные будущие напоминания.

Список «Все», включая просмотр заданий предмета и команду `/tasks all`,
показывает active, собственное done=false и deadline_at строго позже текущего
времени. Фильтр применяется в сервисе и SQL до LIMIT, не после получения страницы.
Срок, равный текущему времени, считается истёкшим. После undo задание вновь
видно, если срок ещё впереди. Другие участники не теряют его из-за чужой отметки.
Данные физически не удаляются. «Просроченные» остаётся отдельным списком;
today/week и явный done-поиск в этих периодах сохраняются. Комбинация all+done
становится недопустимой, чтобы не обходить правило списка «Все».

Кнопки в списках, напоминаниях, дайджесте и новых оповещениях показывают тему.
Пробелы/переводы строк нормализуются, слишком длинная тема сокращается до
60 символов с многоточием. Для совпадающих коротких тем в одном сообщении
добавляется ID. В тексте карточки полная тема и ID сохраняются. Callback view:<ID>
и deep links не меняются.

## Реализация

1. Новая миграция 0004 расширяет outbox для assignment_created и FK assignment_id.
   Существующие 0001–0003 не меняются.
2. Планирование новых событий при публикации; доставка через текущие lease,
   retry_after, rate limiter, quiet hours и worker. Дополнительных постоянных
   сервисов/cron для рассылок нет.
3. Разделение отмены только напоминаний и всех личных уведомлений, чтобы правка
   задания/тихих часов не теряла отложенное оповещение о публикации.
4. Правило «Все» на уровне service/repository и подписи кнопок в transport.
5. Регрессионные тесты, обновление README/ARCHITECTURE/схемы/ADR; test, race,
   lint, build, совокупное покрытие service >=70%.
6. Один Docker-образ с `/app/bot` и `/app/backup`; одноразовый Compose-сервис
   `backup` в профиле `maintenance`. На сервере достаточно Docker Compose,
   Make используется только локально. Образ остаётся без shell.

## Утверждённая миграция

SQLite CHECK старой outbox разрешает только reminder/digest. Поэтому миграция
пересоздаёт outbox: создаёт новую таблицу, копирует все строки и их ID, статусы,
attempts, leases, receipts и payload, удаляет старую таблицу DROP TABLE и возвращает
исходное имя/индексы. Всё выполняется одной транзакцией. Внешних FK на outbox нет.
Новые assignment_id старых строк — NULL. Пользовательские задания/участники
не удаляются. Down отказывается откатываться, если есть assignment_created,
чтобы не потерять события, несовместимые со старой схемой.

Сохраняются все 18 существующих колонок и значения: id, event_key, kind,
reminder_id, digest_run_id, group_id, user_id, part, payload_json, status,
attempts, next_attempt_at, expires_at, lease_token, lease_until, sent_at,
telegram_message_id, last_error_code. Итоговая таблица имеет эти же поля
и одну новую колонку assignment_id. Тесты сравнивают все исходные значения,
ограничения, индексы и работу прежней очереди. Искусственный сбой ради проверки
гарантий SQL-транзакций в этот этап не входит.

## Вспомогательный контейнер резервного копирования

Оператор выполняет `docker compose stop bot`, затем
`docker compose run --rm --no-deps backup`. Служебный контейнер использует
тот же образ, читает volume БД только для чтения и архивирует его целиком,
включая WAL/SHM при наличии, в `./backups` на хосте. Файл получает дату UTC
и случайный суффикс; готовым считается только после успешного закрытия архива
и атомарного переименования временного файла. Ошибки дают ненулевой код.

Контейнер не управляет Docker и не получает Docker socket. Остановка и запуск
бота — явные шаги инструкции. Обновление выполняется только после успешной копии;
при ошибке оператор запускает прежний контейнер `docker compose start bot`.
Для первой копии перед миграцией используется новый служебный образ без запуска
нового бота. Старая рабочая версия остаётся доступна для запуска.

Backup-сервис не запускается обычным `up`. Утилита также проверяет архив и умеет
восстановить его только в пустой каталог нового volume, без перезаписи рабочей БД.
Есть пример серверного Compose без build и пошаговое руководство копирования,
обновления и восстановления. Архивы исключены из Git и Docker build context.
Shell внутри контейнеров не требуется. Служебный процесс root имеет отключённую
сеть и read-only rootfs; токен ему не передаётся.

Агент выполняет миграции только на временных тестовых БД. Рабочая БД, .env,
контейнер и production Compose не изменяются, deployment не выполняется.
Написание и тестирование этой миграции с DROP TABLE разрешено утверждением плана;
применение обновления на сервере остаётся действием владельца.

## Приёмка

- Подтверждение мастера сохраняет задание, требуемые события и аудит;
  проверяется результат публикации, а не транзакционный механизм SQL.
- Каждый подходящий участник получает одно личное оповещение; другие группы,
  поздние участники и выключенные/недоступные личные чаты не получают его.
- Проверены тихие часы, смена настройки, отмена, done/undo, выход, 403, retry,
  повторный запуск и сохранение прежней очереди при миграции.
- Новый тип события не влияет на дневной дайджест и обычные напоминания.
- «Все» скрывает личные done и deadline<=now на каждой странице, не удаляя данные.
  Проверены граница времени, undo, чужая отметка и страницы с большим числом скрытых.
- Все кнопки заданий показывают тему; длинные и одинаковые названия различимы.
- Нет новых env-ключей приложения, callback-форматов, Telegram вызовов из service или SQL из bot.
- Backup-команда создаёт отдельный архив, использует правильный volume и
  не запускает бота, обновление и не модифицирует
  исходную БД. Проверка агентом выполняется только на изолированных тестовых данных.
