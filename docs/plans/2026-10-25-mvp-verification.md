# Проверка полного MVP

Дата: 25.10.2026. Ветка: `chore`.
Основание: утверждённые [план](2026-10-25-mvp.md) и
[контракты](../contracts/mvp.md).

## Результат

Реализованы команды и кнопки Telegram: регистрация, приглашения, членство,
права редакторов, управление группами, привязка чата, предметы, задания,
вложения, личные отметки, настройки, persistent dialogs и аудит.
Эхо больше не используется в штатном запуске приложения.

Напоминания отправляются только лично, автоматические сообщения в группу —
только ежедневный дайджест. Планировщик находится внутри Go-процесса.
Очередь, lease, повторы и подтверждения частей сохраняются в SQLite.

## Функциональная приёмка

- Сквозной Telegram-тест с временной SQLite: admin создаёт группу и предмет,
  назначает editor; участник вступает по коду/deep link; editor публикует задание
  с документом; student открывает карточку, получает файл, ставит и снимает
  отметку; проверяются изменение, отмена, настройки и привязка чата.
- Подмена группы/предмета, доступ чужого участника, недостаточная роль,
  устаревшая версия задания и чужая/старая кнопка диалога отклоняются.
- Два конкурентных шага одной revision: один успешен, второй получает conflict.
  Ошибка завершения мастера полностью откатывает публикацию и напоминания.
- Диалог сохраняется при создании нового сервиса и закрытии/открытии файла БД;
  TTL, отмена, новый ID и очистка payload проверены.
- Миграции Up/Down/Up выполняются только на временных файлах. Обновление схемы
  0001 сохраняет пользователя, группу, роль и исходную дату. 0001 не менялась.
- Проверены будущие интервалы, изменение версии, выполнение/выход/отмена,
  snooze, тихие часы, объединение накопившихся интервалов, пропуск после срока,
  дробный конфигурационный интервал 100ms и повторное планирование без дубля.
- Проверены retry_after, пять попыток, 403 и восстановление доступности после
  личного обращения, истёкший lease и запрет подтверждения старым токеном.
- Дайджест: несколько частей, отдельные receipts, отменённое задание,
  перепривязка после первой части, отсутствие повторной отправки за эту дату,
  пустой следующий день. Персональные отметки в дайджест не попадают.
- Fake Telegram HTTP проверяет getMe/getUpdates, send/edit, callback answer,
  file_id, deep links, проверку администраторов и безопасные коды ошибок.
- Лимитер проверен на общий интервал, личный и групповой чаты и отмену ожидания.
  Scheduler проверен на старт всех задач и завершение по context.
- Fake clock проверяет локальные даты и тихие часы; неоднозначные и
  несуществующие дедлайны при DST отклоняются.

## Проверка Lead

Слои и сервисные интерфейсы сохранены. SQL находится в repository/migrations,
Telegram API — в bot. Связанные изменения выполняются через UnitOfWork;
HTTP выполняется вне транзакции. Обработчики мастеров разделены по шагам.
Новые env-ключи, HTTP API, отдельные сервисы и CI не добавлялись.

Документация обновлена: README, ARCHITECTURE, схема БД и ADR-0008.
SQL-миграции 0002/0003 содержат Up/Down. История и личные отметки при отмене
задания сохраняются; неизменённые вложения не пересоздаются.

## Ограничения и ручная проверка

Живой Telegram с настоящим токеном и существующий контейнер не запускались
и не перезапускались: AGENTS.md запрещает агенту развёртывание и изменение
production-данных. Все функциональные тесты используют вымышленные данные,
временные БД и fake Telegram. Автоматические тесты не пропускались.

После Telegram accept и до DB ack авария может дать дубль. Изменение данных
не гарантирует отзыв уже принятого Telegram HTTP-запроса. Эти границы указаны
в README и ADR; exactly-once не обещается.

Пользовательский `.env`, работающая БД, контейнеры и volumes не изменялись.
Коммиты, PR, merge и deployment не выполнялись. Ручная приёмка и решение о
слиянии остаются за владельцем репозитория. Для проверки в локальном Docker
после просмотра изменений используется документированная команда `make docker-up`.
