# Docker, SQLite и эхо-бот

Статус: утверждено пользователем 2026-10-25; реализовано и проверено.
Результаты: [отчёт о проверке](2026-10-25-verification.md).

Ветка: `chore`. Предыдущие незакоммиченные изменения сохраняются.

## Решение по размещению БД

Пользователь выбрал SQLite внутри контейнера бота с файлом в постоянном
Docker volume. Отдельный сервер БД не требуется. Сохраняются `modernc.org/sqlite`
и сборка без CGO.

## Контракты

### Docker и окружение

- `Dockerfile`: сборка Go 1.27.1 в отдельной стадии; runtime с корневыми
  сертификатами, запуск бинарника от непривилегированного пользователя.
- `docker-compose.yml`: один сервис `bot`, сборка локального образа,
  `env_file: .env`, постоянный именованный volume `bot_data` в `/data`.
- Compose задаёт `DB_PATH=/data/bot.db`; локальный запуск сохраняет значение
  `DB_PATH` из существующей конфигурации. Остальные env-ключи сохраняются.
- `.dockerignore` исключает секреты, `.git`, базы, кеши и результаты сборки.
- Бот использует long polling; входящие порты не публикуются. Один экземпляр
  приложения получает обновления Telegram.
- При остановке отменяются сетевые запросы, прекращается получение обновлений
  и закрывается БД. Ошибки открытия БД, миграций и авторизации Telegram
  завершают запуск ненулевым кодом.
- Пересоздание контейнера сохраняет данные в volume. Команды удаления volume
  не входят в Makefile и не выполняются.

### SQLite

Пакет: `internal/repository/sqlite`.

Предлагаемый API:

```go
func Open(ctx context.Context, path string) (*sql.DB, error)
func Migrate(ctx context.Context, db *sql.DB) error
```

- Создание родительского каталога для файла БД при необходимости.
- `PingContext` при запуске.
- WAL, `foreign_keys=ON` на каждом соединении, `busy_timeout=5000` мс.
- Пул ограничен одним открытым и одним простаивающим соединением.
- SQL находится только в `internal/repository` и `migrations`.
- Время хранится строкой RFC3339 в UTC.
- Отдельные env-ключи для настройки PRAGMA на этом этапе не добавляются.

### Миграции: утверждённое уточнение правил

Перейти от пары `.up.sql` / `.down.sql` к штатному формату goose:
один `NNNN_name.sql` с обязательными секциями `-- +goose Up` и
`-- +goose Down`. Это изменение требуется явно отразить в корневом
`AGENTS.md`, `ARCHITECTURE.md`, README и новом ADR-0007. Существующих миграций
нет; удалять или переименовывать миграции не требуется.

Миграции встраиваются через `embed.FS`. Для применения используется
экземпляр `goose.Provider` и его `Up(ctx)`, чтобы не настраивать глобальное
состояние библиотеки. Это уточняет текущую формулировку про `goose.Up`
в правилах проекта.

Начальная миграция создаёт только основу идентификации пользователей:

| Таблица | Поля и ограничения |
| --- | --- |
| `groups` | `id` INTEGER PK; `title` TEXT NOT NULL; `invite_code` TEXT NOT NULL UNIQUE; `created_at` TEXT NOT NULL |
| `users` | `id` INTEGER PK; `telegram_id` INTEGER NOT NULL UNIQUE CHECK > 0; `display_name` TEXT NOT NULL; `group_id` INTEGER NULL FK → groups.id; `role` TEXT NOT NULL DEFAULT student с CHECK student/editor/admin; `created_at` TEXT NOT NULL |

Удаление группы с существующими пользователями запрещено внешним ключом.
Начальные группы и реальные данные не создаются. Администраторы задаются
через обязательный ADMIN_TELEGRAM_IDS: положительные числовые Telegram ID
через запятую. При запуске после миграций их пользователи создаются с пустым
именем и ролью admin либо получают эту роль. Список является источником прав:
администраторы, исключённые из списка, становятся student. Синхронизация
атомарна и сохраняет имена, группы и исходное created_at. Миграции сами по себе
роли не меняют и списка администраторов не требуют.
Пользователь до появления сценария вступления имеет `group_id=NULL` и роль
`student`. Уникальность `telegram_id` обеспечивает индекс для upsert.

Down удаляет `users`, затем `groups`. Откат проверяется исключительно
на временных тестовых БД. Пользовательская локальная БД не откатывается.

### Репозиторий и сервис

Минимальное представление отправителя в `internal/domain`:

```go
type TelegramUser struct {
    TelegramID  int64
    DisplayName string
}
```

Потребляемый интерфейс определяется в `internal/service`:

```go
type UserRepo interface {
    UpsertTelegramUser(ctx context.Context, user domain.TelegramUser, createdAt time.Time) error
}

type AdminRepo interface {
    SyncAdmins(ctx context.Context, telegramIDs []int64, createdAt time.Time) error
}
```

Upsert создаёт нового пользователя либо обновляет только отображаемое имя.
Повторное обращение не меняет исходные `created_at`, `role`, `group_id`.

Сервис эхо получает репозиторий и функцию времени через конструктор:

```go
func (s *Echo) Reply(ctx context.Context, user domain.TelegramUser, text string) (string, error)
```

Перед ответом сервис сохраняет отправителя. SQL и Telegram API в сервисе
отсутствуют. При ошибке сохранения текст сообщения не возвращается как
успешный ответ.

### Поведение Telegram

- Обрабатываются новые текстовые сообщения от пользователей в личном чате.
- `/start` (включая адресованную боту команду) отвечает:
  «Привет! Пока я работаю в режиме эхо. Отправь мне текст.»
- Прочий текст возвращается без изменений и без Markdown/HTML parse mode.
- Сообщения из групп, сообщения ботов, вложения и служебные обновления
  игнорируются. Это временный контракт до реализации групповых сценариев.
- При ошибке обработки: «Временная ошибка. Попробуй позже.»
- Все обращения к Telegram находятся в `internal/bot`.
- Получение обновлений и HTTP-запросы отменяются через context. Временные
  сетевые ошибки приводят к повтору с задержкой; ошибки авторизации завершают
  работу. Webhook и ожидающие обновления автоматически не удаляются.
- Тексты сообщений и токен не сохраняются в БД и не выводятся в журнал.
  Ошибки клиента Telegram очищаются от URL, содержащих токен.
- Эхо служит проверкой подключения; гарантии доставки ровно один раз
  при аварийном завершении на этом этапе не вводятся.

## План реализации

1. Оформить ADR-0007 и согласованные уточнения правил миграций.
2. Добавить SQLite, embedded-миграцию и интеграционные тесты на временных файлах.
3. Реализовать репозиторий пользователей, сервис эхо и его unit-тесты.
4. Добавить Telegram transport, проверки через поддельный API и сборку
   зависимостей в `cmd/bot`; обновить тесты жизненного цикла.
5. Добавить Dockerfile, Compose и `.dockerignore`.
6. Сделать `make migrate` рабочим через отдельную точку входа для применения
   тех же embedded-миграций. Она читает DB_PATH из `.env`/окружения с прежним
   приоритетом; токен Telegram для миграций не требуется. Отдельный API
   `config.LoadDatabase(ctx context.Context) (string, error)` возвращает только
   путь БД с его проверкой.
7. Добавить и описать Makefile-цели `docker-build`, `docker-up`, `docker-down`,
   `docker-logs`, `docker-check`. `docker-check` проверяет Compose без вывода
   раскрытых переменных окружения. `docker-down` сохраняет volume.
8. Обновить README и фактический статус ARCHITECTURE.md; выполнить Lead-review.

## Критерии приёмки

- На пустом пути БД автоматически создаются файл и схема до запуска polling.
- Повторный старт не повторяет миграции и сохраняет пользователей.
- Уникальность Telegram ID, внешние ключи, UTC-время и сохранение роли/группы
  при upsert проверены интеграционными тестами.
- WAL, foreign_keys и busy_timeout проверены также после открытия нового
  соединения.
- Проверены Up/Down/Up на временной тестовой БД.
- `/start`, эхо, игнорируемые обновления, ошибки и отмена запросов проверены
  через fake API; тесты не отправляют сообщения в настоящий Telegram.
- `make test`, `make test-race`, `make lint`, `make build` проходят.
- `make migrate` работает без BOT_TOKEN и допускает повторный запуск.
- `docker compose config --quiet` проходит, Docker-образ собирается,
  временный контейнер сохраняет тестовые данные после пересоздания.
- При недоступности Docker daemon или сетевого доступа непроведённые проверки
  перечисляются явно. Сейчас Docker CLI/Compose доступны, доступ к daemon из
  сессии ограничен.

## Границы этапа

Задания, расписание, напоминания, членство в группах и интерактивное назначение ролей
появятся следующими отдельными этапами. Продакшен не запускается,
пользовательские данные не изменяются; `.env` не перезаписывается.
